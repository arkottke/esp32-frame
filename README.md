# esp-frame

WiFi-connected e-paper photo frame based on the GDEP133C02 13.3" 6-color ACeP display and ESP32-S3.

Each frame wakes from deep sleep, fetches a pre-rendered image from a local Python server, displays it, and sleeps again. A captive portal handles first-time WiFi setup. Multiple frames are managed through a web UI; content is generated by a plugin system (static images, playlists, weather forecasts, earthquake maps).

---

## Building and Flashing on Arch Linux

### 1. Install system dependencies

```bash
sudo pacman -S python cmake ninja wget git base-devel
```

### 2. Install ESP-IDF v6.0.1

The firmware targets ESP-IDF v6.0.1. Clone it to a stable location:

```bash
mkdir -p ~/esp
git clone -b v6.0.1 --recursive https://github.com/espressif/esp-idf.git ~/esp/esp-idf
~/esp/esp-idf/install.sh esp32s3
```

The install script downloads the Xtensa toolchain, OpenOCD, and Python dependencies into `~/.espressif/`.

### 3. Grant serial port access

On Arch, the serial device group is `uucp`, not `dialout`:

```bash
sudo usermod -aG uucp $USER
```

Log out and back in (or run `newgrp uucp`) for the change to take effect. The device will appear as `/dev/ttyACM0` or `/dev/ttyUSB0` depending on your USB-serial adapter.

### 4. Build

```bash
source ~/esp/esp-idf/export.sh   # activate IDF environment (once per shell)
cd /path/to/esp-frame/firmware
idf.py build
```

On first build, `idf.py` generates `sdkconfig` from `sdkconfig.defaults` and downloads any missing components. This takes a few minutes; subsequent builds are incremental.

> **Upgrading from an older IDF?** Delete `firmware/sdkconfig` before building so it is regenerated clean from `sdkconfig.defaults`. Stale Kconfig keys from a previous version cause hard-to-diagnose errors.

### 5. Flash

```bash
idf.py flash
```

If the device is not auto-detected, specify the port:

```bash
idf.py -p /dev/ttyUSB0 flash
```

### 6. Monitor serial output

```bash
idf.py monitor
# or combined with flash:
idf.py -p /dev/ttyACM0 flash monitor
```

Exit the monitor with `Ctrl-]`.

### 7. Re-run menuconfig (optional)

If you need to change any Kconfig options (e.g. log level, partition table):

```bash
idf.py menuconfig
```

Changes are written to `sdkconfig`. Commit `sdkconfig` if you want reproducible builds; leave it in `.gitignore` if you rely on `sdkconfig.defaults` only.

## Server Setup

```bash
cd server
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --host 0.0.0.0 --port 8000 --reload
```

Open `http://localhost:8000/` to manage frames.

### Test image dithering

```bash
python dither.py encode photo.png   # produces photo.epd (960 000 bytes)
python dither.py decode photo.epd   # produces photo_preview.png for visual verification
```

### Running with Docker Compose

`server/Dockerfile` builds an image that serves both the FastAPI app (default `CMD`) and the Telegram bot (`telegram_bot.py`), selected via the `command:` override. Neither reads a config-path env var — the FastAPI app resolves `config.json` and `uploads/` relative to `server/` inside the container (`/app/config.json`, `/app/uploads`), and the bot writes to a fixed `/app/gallery`. Bind-mount those paths at exactly `/app/config.json`, `/app/uploads`, and `/app/gallery` to persist data across restarts and rebuilds.

To fold this into an existing `docker-compose.yml`:

```yaml
services:
  esp-frame:
    build: ./esp-frame/server        # path to this repo's server/ dir
    image: esp-frame-server
    restart: unless-stopped
    ports:
      - "8000:8000"
    volumes:
      - ./esp-frame/data/config.json:/app/config.json
      - ./esp-frame/data/uploads:/app/uploads

  esp-frame-telegram-bot:
    image: esp-frame-server           # reuse the same built image
    restart: unless-stopped
    command: ["python", "telegram_bot.py"]
    environment:
      TELEGRAM_BOT_TOKEN: ${TELEGRAM_BOT_TOKEN}
      TELEGRAM_ALLOWED_CHAT_ID: ${TELEGRAM_ALLOWED_CHAT_ID}
    volumes:
      - ./esp-frame/data/gallery:/app/gallery
    depends_on:
      - esp-frame
```

Set `TELEGRAM_BOT_TOKEN` (and optionally `TELEGRAM_ALLOWED_CHAT_ID`) in the `.env` file next to your compose file — Compose loads it automatically for `${...}` substitution. `config.json` is a *file* bind-mount, not a directory, so create an empty `config.json` (e.g. `{}`) on the host before the first `up`, or Docker will create a directory there instead.

## First-time Frame Setup

1. Flash the firmware.
2. On first boot the frame creates a WiFi access point named **`ESP-Frame-XXXXXX`**.
3. Connect to it and navigate to **`http://192.168.4.1/`**.
4. Enter your WiFi credentials, server URL (e.g. `http://192.168.1.10:8000`), and poll interval.
5. The frame restarts, joins your network, and begins polling.

To reset a frame back to provisioning mode, hold **SW4 (IO14)** for 5 seconds on boot.

## Button Polarity: All Three Are Active-HIGH

Per the board manual, **SW2, SW3, and SW4 are all triggered by a high level**
(idle LOW, pressed HIGH) — there is no hardware fault on any of them. This
matters because a past firmware regression assumed SW2 was active-LOW (idle
HIGH) and armed the deep-sleep wakeup on `ESP_EXT1_WAKEUP_ANY_LOW`. Since SW2's
real idle state is LOW, that wakeup condition was satisfied the instant the
chip went to sleep — the frame never actually slept, looping connect/fetch/sleep
continuously, which (combined with the LOAD_SW rail issue above) is what
drained the battery in about a week instead of months.

Firmware now configures SW2 with an internal pull-down and wakes on
`ESP_EXT1_WAKEUP_ANY_HIGH`, matching SW4's existing (and always correct)
active-HIGH handling. If you add SW3 to firmware in the future, configure it
the same way.
